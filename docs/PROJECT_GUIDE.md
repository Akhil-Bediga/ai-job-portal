# AI Job Portal &mdash; Project Guide

A walkthrough of the whole project: what it is, how the pieces fit together,
how to run it, and how to talk about it. The [README](../README.md) is the
front page; this document is the deeper dive.

---

## 1. What this project is

A job portal where the user pastes a resume and gets the best-matching open
roles, ranked by an NLP recommender. Behind that simple UX is a complete data
pipeline:

- **Synthetic job postings and resumes** are generated by Faker, with a hidden
  "job family" tag attached to each (only used to score the recommender, never
  shown to it).
- **A Pandas ETL** cleans the postings, normalizes salaries and enums, and
  extracts the skills mentioned in each description.
- **Two stores** receive the output:
  - **MySQL** holds the structured, queryable columns (`jobs`, `job_skills`).
  - **MongoDB** holds the unstructured side &mdash; full descriptions, extracted
    skill lists, and resume documents.
- **A recommender** built on a hand-rolled NumPy TF-IDF blends text cosine
  similarity with skill-set Jaccard overlap to rank jobs for a resume.
- **A Flask REST API** exposes search, parsing, recommendation, and stats
  endpoints, and serves a vanilla HTML/CSS/JS frontend.
- **Matplotlib dashboards** read the warehouse and write five PNGs to
  `docs/dashboards/`.
- **A reproducible benchmark** scores the engine vs. a keyword-overlap baseline
  on 240 held-out resumes and reports the uplift.

The whole thing is in one repo, runnable with Docker Compose + a virtualenv.

## 4. Tech stack and why each piece was picked

- **Python 3.10+** &mdash; everything is in Python, including the recommender,
  so there's one runtime and one set of tooling.
- **Pandas + NumPy** &mdash; the ETL is a few small DataFrame transforms, and
  TF-IDF / cosine similarity are linear algebra. NumPy is enough, no
  scikit-learn needed.
- **Faker** &mdash; real job boards forbid scraping and rate-limit; synthetic
  data is the only way to ship something reproducible. Faker gives realistic
  companies, cities, and names.
- **MySQL 8** &mdash; the structured store. Good for filters and aggregates
  (the analytics views).
- **MongoDB 7** &mdash; the document store. Free-form text and variable-length
  skill arrays per posting fit naturally as documents.
- **Flask** &mdash; minimal REST API framework. Three files, no boilerplate.
- **vanilla HTML/CSS/JS** &mdash; the frontend is one page; a framework would
  add ten times the code for no win.
- **Matplotlib** &mdash; static PNGs that can be embedded in the README and
  shared without a server.
- **Docker Compose** &mdash; one command to bring up both databases. The
  alternative (installing MySQL and MongoDB locally) is fragile and varies by
  OS.
- **pytest** &mdash; the standard. Tests run in under a second.

What's deliberately **not** in the stack:

- **scikit-learn** &mdash; building the vectorizer in NumPy is the whole point
  of the "Python + NumPy + NLP" bullet on the resume. It's also a few dozen
  lines.
- **A frontend framework** &mdash; React/Vue/etc. add weight and tooling for a
  single page.
- **Real scraping** &mdash; against the terms of every major job board.

## 6. Module-by-module walkthrough

### 6.1 `src/data_generator.py`

Produces three files into `data/raw/`:

- `jobs.csv` &mdash; structured columns (job_id, title, company, family, city,
  state, remote, employment_type, seniority, salary_min, salary_max,
  posted_date).
- `jobs_text.json` &mdash; `{job_id: description_text}`.
- `resumes.json` &mdash; `[{resume_id, family, text}, ...]`.

Each posting and resume carries a hidden `family` (Data Engineer, Frontend
Engineer, etc.) that's used only by the benchmark to score rankings. The
descriptions are assembled from a small grammar:

```
intro (varied) + filler (5 generic lines) + responsibilities (3, family skills)
+ requirements (2) + nice-to-have skills + outro (varied)
```

A fraction of resumes (~35%) are **hybrid** &mdash; they pull responsibilities
and skills from a *related* family in the same cluster (data roles share a
cluster; web roles another). That mirrors real candidates who have a foot in
two fields and pulls the recommender off a suspicious perfect score.

The data is seeded (`Faker.seed(42)`, `random.seed(42)`, `np.random.seed(42)`),
so regenerating gives identical output.

### 6.2 `src/nlp/` &mdash; the NLP layer

Three small modules, all offline (no nltk/spaCy downloads).

- **`preprocess.py`**
  - `words(text)`: lowercase, regex-tokenize (`[a-z0-9][a-z0-9+#./-]*`), strip
    sentence punctuation, drop empties. Keeps `c++` and `c#` intact.
  - `tokenize(text)`: same as `words`, then drop a bundled English stopword
    list plus 1-char and pure-number tokens. Used by the TF-IDF vectorizer.
  - `STOPWORDS`: a bundled frozenset.
- **`skills.py`**
  - Loads `data/skills.txt` (sorted longest-phrase first).
  - `extract_skills(text)`: scans the token sequence and matches gazetteer
    entries, consuming every occurrence so a repeated `"apache spark"` can't
    leave a bare `"spark"` token for the shorter entry to grab.
- **`vectorizer.py`**
  - `TfidfVectorizer(min_df, max_df)`:
    - `fit(docs)`: builds `vocabulary_` (term → index) and `idf_` array using
      smoothed IDF: `idf[t] = ln((1+N)/(1+df[t])) + 1`.
    - `transform(docs)`: term-frequency matrix, multiplied column-wise by the
      IDF vector, then L2-normalized.
    - `fit_transform`: convenience.
  - `cosine_sim(a, b)`: row-wise cosine between two matrices, with safe
    handling of all-zero rows via `l2_normalize`.

The whole TF-IDF implementation is about 40 lines of NumPy. That's
intentional: it directly substantiates the "Python + NumPy + NLP" bullet
rather than hiding behind a library import.

### 6.3 `src/etl/` &mdash; extract, transform, load

- **`extract.py`** &mdash; reads the three raw files into a `RawData`
  dataclass. No remote calls; the data generator writes to disk, the ETL reads
  from disk.
- **`transform.py`**
  - `_clean_jobs`: dedup by `job_id`, fillna, string slicing for column-width
    safety, swap reversed `salary_min`/`salary_max`, derive `salary_avg`,
    coerce date, validate enums (`employment_type`, `seniority`).
  - `_extract_features`: for every posting, call `extract_skills(text)` and
    build (a) `job_skills` rows for MySQL and (b) `job_docs` for MongoDB.
  - Resumes pass through with their extracted skills attached.
- **`load.py`** &mdash; idempotent dual load.
  - MySQL: `SET FOREIGN_KEY_CHECKS=0` → `TRUNCATE job_skills` →
    `TRUNCATE jobs` → re-enable checks → bulk `to_sql` append for both tables.
  - MongoDB: `delete_many({})` then `insert_many(...)` for `job_text` and
    `resumes`. Indexes are created idempotently on `job_id`, `skills`, and
    `resume_id`.

### 6.4 `src/reco/` &mdash; the recommender

- **`engine.py`**
  - `JobDoc(job_id, text, skills)` is the input shape.
  - `Recommender.fit(jobs)`: tokenizes every job description and fits a
    `TfidfVectorizer`, producing a `(n_jobs × vocab_size)` matrix.
  - `_scores(resume_text)`: vectorizes the resume, computes text cosine
    against every job (a single matrix multiply because rows are normalized),
    and computes Jaccard overlap against each job's skill set.
  - `rank_all` / `recommend`: combines the two signals with
    `score = 0.6 * text + 0.4 * skill`, sorts, and attaches matched / missing
    skills per job.
- **`baseline.py`** &mdash; the comparison point. Same input, but builds a
  raw term-frequency matrix from `words(text)` (stopwords *kept*), L2
  normalizes, and ranks by cosine. No IDF, no skills, no preprocessing
  filters. The naive thing anyone would try first.

### 6.5 `src/api/` &mdash; the REST API

- **`app.py`**: a thin `create_app` factory; registers the blueprint, sets
  `static_folder = frontend/` so Flask serves the UI on the same origin.
- **`service.py`**: a singleton `RecoService` that lazy-loads the recommender
  from MongoDB on first call and caches a `job_id → metadata` map from MySQL
  for rendering match results. `reload()` rebuilds both after a pipeline run.
- **`routes.py`**: the nine endpoints below. SQL goes through `get_engine`,
  recommendations through the service.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | liveness + whether the model is loaded |
| GET | `/api/jobs?q=&family=&limit=` | search/list postings |
| GET | `/api/jobs/<job_id>` | full posting + skills |
| POST | `/api/resume/parse` | resume → extracted skills + counts |
| POST | `/api/recommend` | resume → ranked matches |
| GET | `/api/stats/skills?limit=N` | top in-demand skills |
| GET | `/api/stats/salary` | salary stats by role |
| GET | `/api/stats/families` | postings per role |
| POST | `/api/reload` | rebuild the in-memory model |

### 6.6 `frontend/` &mdash; the UI

Three files, no build step. `index.html` lays out the page (resume textarea,
results, stats sidebar). `styles.css` is a clean blue-on-white CSS Grid layout
with mobile collapse. `app.js` does the work: fetch from same-origin
`/api/...`, render match cards with score percentages and matched / missing
skill chips, populate the sidebar bars with skill demand and avg salary.

### 6.7 `src/analytics/dashboards.py`

Five Matplotlib charts written to `docs/dashboards/`:

1. **Top 15 in-demand skills** &mdash; horizontal bar from MySQL `job_skills`.
2. **Average salary by role** &mdash; horizontal bar from MySQL `jobs`.
3. **Open postings by role** &mdash; vertical bar from MySQL `jobs`.
4. **Salary distribution** &mdash; histogram across all postings.
5. **Best-match score distribution** &mdash; runs the live recommender over
   every resume in MongoDB and histograms the top match score per resume.

The visual style is set once in `plt.rcParams` (white background, soft grid,
no top/right spines).

### 6.8 `benchmarks/eval_reco.py`

Runs both the engine and the baseline over all 240 resumes against all 1,200
postings. For each resume:

- **Relevant set** = postings with the same family as the resume.
- **Ranked list** = sorted by model score.

Reports three metrics:

- **Precision@10** &mdash; fraction of the top 10 that are relevant.
- **NDCG@10** &mdash; discounted-cumulative-gain at 10, normalized by the
  ideal ranking.
- **MRR** &mdash; reciprocal rank of the first relevant result.

Writes `results.json`. Runs straight off `data/raw/`, no database required.

## 7. The data model

### 7.1 MySQL

```
jobs
├─ job_id          VARCHAR(36)  PK
├─ title           VARCHAR(160)
├─ company         VARCHAR(120)
├─ family          VARCHAR(60)   -- analytics + eval tag
├─ city, state, remote
├─ employment_type ENUM(FULL_TIME, PART_TIME, CONTRACT)
├─ seniority       ENUM(JUNIOR, MID, SENIOR, LEAD)
├─ salary_min, salary_max, salary_avg
└─ posted_date     DATE

job_skills
├─ id      BIGINT PK
├─ job_id  → jobs.job_id  (FK, ON DELETE CASCADE)
└─ skill   VARCHAR(80)    -- one row per (job, skill)
```

Indexes: `(family)`, `(seniority)`, `(state)`, `(title)`, `(skill)`,
`UNIQUE(job_id, skill)`.

### 7.2 MongoDB

```
job_text  one document per posting
{
  job_id:  string,
  family:  string,
  text:    string,    // full description
  skills:  [string]   // extracted by the gazetteer
}
indexes: { job_id: unique }, { skills }

resumes  one document per resume
{
  resume_id: string,
  family:    string,
  text:      string,
  skills:    [string]
}
indexes: { resume_id: unique }
```

Why two stores? MySQL is great for filters and aggregates the API needs
(`WHERE family = ?`, `GROUP BY family`). MongoDB is great for variable-length
text and skill arrays the recommender consumes. Splitting the responsibilities
keeps each store doing what it's good at.

## 8. The recommender, in math

For a resume `r` and a job `j`:

```
text_sim(r, j) = cos(tfidf(r), tfidf(j))      # in [0, 1]
skill_sim(r, j) = |Skills(r) ∩ Skills(j)|     # Jaccard
                 ─────────────────────
                 |Skills(r) ∪ Skills(j)|

score(r, j) = 0.6 · text_sim + 0.4 · skill_sim
```

- `tfidf(d)` is `tf(d) * idf` element-wise, L2-normalized, where
  `idf[t] = ln((1+N)/(1+df[t])) + 1`.
- Because rows are L2-normalized, `cos(u, v) = u · v`, so scoring 1 resume
  against `N` jobs is a single `(1×V) · (V×N) = (1×N)` matrix multiply.
- The `0.6 / 0.4` blend is tuned to the dataset; the text and skill signals
  are complementary &mdash; text catches phrasing the gazetteer misses, skills
  catch the hard requirements text matching glosses over.

## 9. The benchmark, in detail

Ground truth: a posting is **relevant** to a resume if they share a family
tag. Family tags are baked into the synthetic data but never fed to either
model &mdash; both models see only text and (for the engine) extracted skills.

**Why a baseline?** Without one, you can't claim improvement &mdash; an
absolute precision@10 of 0.98 is meaningless without a reference. The
keyword-overlap baseline (raw TF cosine, no IDF, no stopword removal, no skill
extraction) is the obvious naive thing anyone would try. The uplift over it is
the legitimate value the engine adds.

**Why the gap exists:** Every posting and resume includes shared boilerplate
("we move fast", "competitive benefits", "strong communication skills"). A
raw keyword match weights that boilerplate as heavily as actual skills, so
boilerplate-heavy postings get pulled toward every resume regardless of role.
TF-IDF down-weights terms that appear in most documents (high document
frequency → low IDF), so the engine effectively ignores the boilerplate. The
skill Jaccard adds a second, complementary signal that keys on the hard
requirements.

**Final results** (from `benchmarks/results.json`):

| Metric | Baseline | Engine | Uplift |
|---|---:|---:|---:|
| Precision@10 | 0.748 | 0.981 | **+31.1%** |
| NDCG@10 | 0.771 | 0.982 | **+27.4%** |
| MRR | 0.907 | 0.989 | +9.0% |

(MRR is high for both because the first relevant result is usually near the
top &mdash; the metric is most useful when models occasionally surface
relevant items deep in the list.)

## 12. Talking points (interviews / portfolio reviews)

Common questions and how to answer them with this project as your reference.

**"Walk me through this project."**

> It's a job portal with an NLP recommender on top. The data flow is: synthetic
> postings and resumes from a generator, a Pandas ETL that cleans and extracts
> skills, then a split into MySQL for structured columns and MongoDB for
> unstructured text. The recommender is a hand-rolled NumPy TF-IDF blended
> with a Jaccard skill overlap. A Flask API exposes the search and
> recommendation endpoints and serves a vanilla JS frontend. There's also a
> reproducible benchmark that shows the engine beats a keyword baseline by 31%
> on precision@10.

**"Why two databases?"**

> Different shapes. The structured columns (`title`, `company`, `salary_avg`,
> `family`) are perfect for SQL filters and aggregations, which is what the
> stats endpoints do. The unstructured side &mdash; full descriptions and
> variable-length skill arrays &mdash; is a natural document shape. Putting
> each in the store that fits keeps both queries simple. The API joins them by
> `job_id` when it needs both.

**"Why TF-IDF and not embeddings?"**

> TF-IDF is interpretable, deterministic, and runs in tens of milliseconds on
> a thousand documents with no model to load. It also benchmarks 31% above a
> keyword baseline on this dataset, so the added complexity of a sentence
> transformer wasn't justified. If I were extending this, the natural next
> step would be a small embedding model for re-ranking the top 50 candidates
> &mdash; classic retrieve-then-rerank.

**"How is the recommender scored?"**

> Every resume has a hidden family tag, which is also on every posting.
> Relevant = same family. I rank all 1,200 postings for each of 240 resumes
> with both the engine and a naive keyword baseline, and average precision@10,
> NDCG@10, and MRR across the resumes. The engine scores 0.981 precision@10
> vs. 0.748 for the baseline, a 31% lift &mdash; reproducible with one
> command. The numbers are in `benchmarks/results.json`.

**"Why does the baseline lose by that much?"**

> Both postings and resumes contain a lot of shared boilerplate
> &mdash; "competitive benefits", "strong communication", "fast paced
> environment". A raw keyword match counts every word equally, so boilerplate
> drowns out the real skill signal. TF-IDF down-weights anything that appears
> in most documents, so the engine effectively ignores the boilerplate, and
> the skill-overlap term keys on hard requirements that text matching glosses
> over.

**"Why did you build TF-IDF by hand instead of using scikit-learn?"**

> Two reasons. The math is short &mdash; about 40 lines of NumPy &mdash; and
> doing it by hand demonstrates I actually understand it rather than treating
> it as a black box. Second, it kept the dependency list smaller and the
> startup time shorter for the API.

**"How does the skill extraction work?"**

> A gazetteer in `data/skills.txt` listing ~100 skills, including multi-word
> phrases like "apache spark" and "machine learning". I sort the list
> longest-phrase-first and scan the tokenized text, consuming matched tokens.
> Consuming every occurrence is important &mdash; otherwise a second
> "apache spark" leaves a bare "spark" token for the shorter entry to grab.

**"What would you do with another two weeks?"**

> Three things. First, a small sentence-transformer re-ranker over the top 50
> &mdash; classic retrieve-then-rerank, would lift NDCG meaningfully. Second,
> swap the synthetic data for a real corpus (e.g., a snapshot of an open job
> dataset like the EMSI sample). Third, add learning-to-rank using
> click-through signals if I had user interactions to feed it.

## 13. Troubleshooting

**`Connection refused` on the API or pipeline**

The databases aren't up. Run `docker compose ps`. If they're missing or
unhealthy, `docker compose up -d` and wait ~10 seconds. If Docker Desktop is
paused, unpause it via the whale-menu / Dashboard.

**`Table 'jobportal.jobs' doesn't exist`**

The schema wasn't applied. Run:

```bash
docker exec -i jobs-mysql mysql -uroot -prootpass < sql/schema.sql
```

**`/api/recommend` returns `{"error": "missing 'text'"}`**

The request body must be JSON with a `text` field. Make sure
`Content-Type: application/json` is set.

**The frontend shows "Stats unavailable"**

The pipeline hasn't run, so the databases are empty. Run
`python -m src.pipeline` then refresh the page.

**`pip install` fails on `pandas` or `numpy`**

You're probably on an old Python. The project tested on 3.10 through 3.14;
upgrade if you're below 3.10.

**The benchmark number is different from 31.1%**

Did you change `JOB_FILLER`, `RESUME_FILLER`, `HYBRID_PROB`, or `N_RESP` in
`src/data_generator.py`? The default values are tuned. The seeds (`42`) keep
the data deterministic; with the defaults plus the seeds, the result should
be 31.1% to one decimal.

## 14. Extension ideas (later, if you want)

- **Real data**: swap the synthetic generator for a real corpus. The EMSI /
  Lightcast open dataset and the Kaggle "LinkedIn Job Postings" set are good
  starting points.
- **Embedding re-ranker**: keep TF-IDF as the recall layer; re-rank the top 50
  with a small sentence-transformer (e.g. `all-MiniLM-L6-v2`).
- **Learning-to-rank**: capture click-through on the frontend, train a small
  pairwise ranker offline.
- **Resume file upload**: parse `.pdf` / `.docx` resumes using PyMuPDF or
  python-docx; right now `POST /api/resume/parse` takes plain text.
- **Auth + saved searches**: add user accounts so people can save resumes
  and get email alerts when new matches appear.
- **A second baseline**: a BM25 ranker, to show TF-IDF isn't free either
  &mdash; a more honest comparison.
- **Production-ize**: gunicorn instead of Flask's dev server, Alembic for
  schema migrations, GitHub Actions for CI.
